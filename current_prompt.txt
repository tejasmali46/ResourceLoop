# ResourceLoop — Complete Authentication, Administration & Event Flow Integration

## 1. Project Context and Primary Objective

You are working on my **existing ResourceLoop project**, a role-based institutional resource-sharing platform for colleges.

The platform supports sharing and booking institutional resources such as projectors, microphones, speakers, laboratories, 3D printers, classrooms, seminar halls, and event venues. Students and clubs can request resources or organize events, while faculty coordinators, HODs, resource managers, and administrators manage approvals and institutional operations.

Your task is to properly integrate and fix:

1. A complete, reliable login and authentication system for every existing role.
2. Correct role-based authorization and dashboard access.
3. Complete administration and user management.
4. A properly connected event submission and approval flow.
5. Regression testing to ensure all existing features continue to work.

**This is an enhancement of the existing project, NOT a new project or a complete rewrite.**

**Preserve the existing UI, layout, design, dashboards, and functionality. Make only the minimum necessary changes.**

## 4. Secure Authentication and Session Management

Implement security using the existing backend framework and authentication libraries where possible.

Requirements:

- Hash passwords securely using an established password-hashing algorithm, such as Argon2id or bcrypt.
- Never store or return plaintext passwords.
- Do not expose password hashes, secrets, session tokens, or sensitive account information in API responses or logs.
- Validate and sanitize user inputs appropriately.
- Use secure session cookies where applicable, including appropriate HttpOnly, Secure, and SameSite settings.
- If the project uses token-based authentication, validate tokens correctly and handle expiration and revocation appropriately.
- Implement CSRF protection where required by the chosen authentication strategy.
- Protect against unauthorized access, privilege escalation, and insecure direct object references.
- Add sensible login error handling and rate limiting where appropriate.
- Ensure logout invalidates the relevant session or token according to the existing architecture.
- Provide or repair a current-user endpoint, such as the existing equivalent of `/me`, if needed by the frontend.
- Never return privileged information to users who lack permission to access it.

### Existing user migration

If existing user records use an incompatible password format:

1. Inspect the current storage and authentication logic.
2. Implement a safe migration or password-reset strategy.
3. Preserve existing user accounts, IDs, departments, booking records, event records, and audit history.
4. Do not silently reset everyone's password or delete existing accounts.
5. Do not claim existing passwords work unless they have been verified.

Do not introduce destructive database migrations.

## 5. Proper Role-Based Access Control (RBAC)

Authentication determines who the user is. Authorization determines what that user can do.

Enforce authorization on the backend for all protected operations. Hiding buttons in the frontend is not sufficient.

### Student / Club Representative

Must be able to perform the actions permitted by the existing student role, such as:

- Access their own dashboard.
- Discover available resources.
- View eligibility requirements and availability.
- Submit resource booking requests.
- Submit event requests.
- View their own event and booking statuses.
- Review approval feedback and rejection reasons.
- Access their own permitted booking history, notifications, and records.
- Complete check-in/check-out actions when authorized by the existing workflow.

Students must not approve their own requests, assign privileged roles, or modify other users' records without explicit authorization.

### Faculty Coordinator

Must be able to:

- Access the existing faculty dashboard.
- View event and resource requests assigned to them.
- Review requests from the appropriate students, clubs, and departments.
- Approve, reject, or return requests for correction where supported.
- Provide comments or reasons for decisions.
- Forward requests to the HOD or another required approver.
- View relevant event details, resource requirements, and approval history.
- Access only the departments, clubs, or requests they are authorized to manage.

### HOD / Department Approver

Must be able to:

- Access the existing HOD dashboard.
- View requests requiring HOD or department-level approval.
- Approve or reject requests within their authority.
- Review faculty recommendations and approval history.
- View relevant department events and resource requirements.
- Ensure decisions are recorded in the database.
- Avoid approving requests outside their assigned department or authorization scope unless explicitly permitted.

### Resource Manager / Lab In-charge

Must be able to:

- Access the existing resource manager dashboard.
- Manage resources within their assigned responsibility.
- Review assigned resource bookings.
- Verify availability, capacity, scheduling, and conflicts.
- Confirm or reject resource allocation according to existing rules.
- Manage check-in/check-out and condition records where authorized.
- Record damage, delays, and incidents where supported.
- Prevent unauthorized modifications to resources managed by other users.

### Institution Administrator

Must be able to access the existing administration dashboard and perform the administrative actions explicitly authorized by the application.

An administrator must not automatically bypass every business rule unless the existing system or institutional policy permits it.

### Backend authorization rules

- Apply role and ownership checks to protected API endpoints.
- Verify department and resource scope where applicable.
- Prevent students from accessing other students' private records.
- Prevent users from changing their own role through API requests.
- Prevent unauthorized approval, event modification, resource allocation, or account administration.
- Use centralized authorization middleware or existing equivalent patterns where practical.
- Return appropriate HTTP status codes for unauthenticated and unauthorized requests.

## 7. FINAL CHANGE: Fix and Connect the Complete Event Flow

This is a specific requested enhancement. Inspect the current event workflow and correct the missing or broken connections while preserving the existing project.

Do not build a separate event management system.

### Step 1: Event creation and submission

A student or authorized club representative must be able to create and submit an event request using the existing event form and workflow.

Preserve the existing fields and validation rules. Where supported, an event may contain:

- Event name and description.
- Organizing student or club.
- Department.
- Event date and time.
- Venue or resource requirements.
- Expected attendance or capacity.
- Equipment requirements.
- Supporting information.
- Any other fields already present in the project.

Validate required fields, event dates, user permissions, and resource requirements on the backend.

When submitted, the event must actually be saved to the database and receive the appropriate initial status. Do not merely display a frontend success message.

### Step 2: Route requests to the correct approvers

This is critical: **event requests must reach the correct faculty coordinator and HOD when their approval is required.**

Inspect the existing department, club, faculty, and HOD relationships to determine how requests should be routed.

- Associate the event with the correct student or club and department.
- Identify the relevant faculty coordinator using existing assignments or relationships.
- Route the request to the correct faculty coordinator.
- Where institutional rules require HOD approval, forward the request to the appropriate HOD after the required prior approval.
- If resource manager approval or confirmation is also required, include it at the appropriate stage.
- Use the existing workflow rules and preserve any existing approval order.
- Do not route every request to an arbitrary faculty member, a hardcoded account, or every HOD.
- Do not automatically approve a request simply because no approver was found.

If the required approver is missing, show a meaningful pending-routing or configuration error and record the issue appropriately. Do not silently discard the request.

### Step 3: Faculty review

The assigned faculty coordinator must be able to see submitted events requiring their review in the existing faculty dashboard.

The faculty coordinator must be able to perform the permitted actions, such as:

- Review event information and requested resources.
- Approve the faculty review stage.
- Reject the request with a reason.
- Request corrections where supported.
- Forward the request to the HOD or next required approver.

Every decision must be validated on the backend and persisted in the database.

### Step 4: HOD / department approval

Where HOD approval is required:

- The event must appear in the correct HOD dashboard after the preceding required stage is complete.
- The HOD must be able to review the request and its prior decisions.
- The HOD must be able to approve or reject the request within their authority.
- A rejection must include a reason where required by the existing workflow.
- The decision must update the event's actual persisted status and approval history.

Do not allow an HOD to approve a request that has not completed the required previous approval stages unless existing policy explicitly permits it.

If the current system supports different approval paths for different event types, departments, or resource categories, preserve them.

### Step 5: Resource availability and confirmation

If an event requires a venue, laboratory, equipment, or other bookable resource:

- Integrate the event with the existing resource-booking system.
- Check resource availability for the requested time.
- Check for scheduling conflicts and capacity restrictions.
- Follow the existing resource allocation and approval rules.
- Route the booking to the appropriate resource manager when required.
- Prevent conflicting confirmed bookings.
- Ensure the event and its resource booking remain correctly associated.
- Avoid creating duplicate bookings when the same event is reviewed or resubmitted.

Do not mark a venue or resource as confirmed until the required approval and allocation steps have succeeded.

If an event does not require a bookable resource, do not force it through an unnecessary resource-booking stage.

### Step 6: Event status and approval history

Ensure event statuses are consistent across all relevant dashboards and API responses.

Reuse the existing status names and transitions wherever possible. Depending on the current implementation, statuses may include:

- Draft
- Pending
- Under Review
- Pending Faculty Approval
- Pending HOD Approval
- Pending Resource Confirmation
- Approved
- Rejected
- Changes Requested
- Cancelled
- Completed

These are examples, not a requirement to introduce every status. Use the project's current status model and only add a state when it is genuinely necessary for the existing workflow.

Requirements:

- Update the database status whenever an authorized action occurs.
- Ensure the student, faculty, HOD, resource manager, and administrator see the appropriate current status.
- Record the decision-maker, action, timestamp, and reason where supported.
- Preserve the previous approval history.
- Prevent invalid transitions, duplicate approvals, and unauthorized status changes.
- Ensure the event creator cannot directly change an event to Approved.
- Ensure a rejected event does not continue to later approval stages unless the existing resubmission workflow explicitly allows it.

### Step 7: Notifications and event visibility

Use the existing notification system if available.

Notify the relevant users when:

- An event is submitted.
- A request becomes available for faculty review.
- Faculty approval is completed or a rejection occurs.
- HOD approval is required or completed.
- Resource confirmation is required or completed.
- An event is approved, rejected, or returned for corrections.
- A significant event status changes.

Do not create a duplicate notification system unnecessarily.

Ensure each user sees only the events and information permitted by their role, ownership, department, and assigned responsibilities.

### Step 8: Cancellation, resubmission, and existing event features

Preserve and verify any existing cancellation, resubmission, editing, event-history, reporting, and audit functionality.

If an event is edited or resubmitted:

- Apply the existing validation and approval rules.
- Invalidate or repeat approvals only when required by the current business rules.
- Preserve previous decision history.
- Recheck resource availability if the date, time, venue, or equipment changes.
- Avoid duplicate records or inconsistent statuses.

Do not remove existing event features just because they are not explicitly listed here.
